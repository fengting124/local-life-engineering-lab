## 1. 最终目标

项目最终需要同时满足四个条件：

1. 核心交易链路在并发、重复请求、服务重启和中间件故障下保持可解释的正确性。
2. 本地 Demo 可在普通开发机上启动，默认不依赖 etcd、MinIO 和独立 Milvus 服务。
3. Agent、RAG、HITL、Checkpoint、MCP 的设计都有代码、测试、指标和失败兜底支撑。
4. 面试时每个技术点都能回答业务问题、设计选择、替代方案、故障模式和验证方法。

## 2. 执行约束

1. 每个阶段单独提交，提交信息使用 `fix`、`feat`、`test`、`docs` 前缀。
2. 每次修改必须包含测试或可重复的 smoke 脚本。
3. 不新增与当前问题无关的中间件。
4. 不使用仅存在于注释中的“生产级”表述。能力未完成时明确标注当前边界。
5. 所有状态迁移使用条件更新、唯一约束或幂等账本形成最终兜底。
6. 网络调用、模型调用、MQ 发送不得持有数据库行锁。
7. 默认本地运行路径保持轻量，完整基础设施通过可选 profile 启动。

## 4. 阶段 A：交易与消息正确性加固

### A1. Outbox 多实例领取租约

#### 当前问题

多个 Relay 实例可以同时查询同一条 `PENDING` 消息。现有 `markAsSent` 只能防止重复更新状态，无法阻止多个实例在更新前重复发送 MQ。

#### 表结构

新增迁移：

`local-life-server/src/main/resources/db/migration/V11__harden_outbox_claim.sql`

新增字段：

```sql
status          VARCHAR(20) NOT NULL
worker_id       VARCHAR(64) NULL
lease_until     DATETIME NULL
claimed_at      DATETIME NULL
version         INT NOT NULL DEFAULT 0
```

状态机：

```text
PENDING -> PROCESSING -> SENT
                      -> PENDING
                      -> FAILED
```

索引：

```sql
KEY idx_outbox_claim(status, next_retry_at, lease_until, id)
```

#### 代码修改

1. `OutboxMessage.java` 增加租约字段。
2. `OutboxMessageMapper.java` 增加：
   - `selectClaimCandidatesForUpdateSkipLocked(limit)`
   - `markProcessing(id, workerId, leaseUntil)`
   - `markSent(id, workerId)`
   - `markRetryFromProcessing(...)`
   - `requeueExpiredLeases(now)`
3. 新增 `OutboxClaimService.java`，使用短事务完成 `SELECT ... FOR UPDATE SKIP LOCKED` 和状态领取。
4. `OutboxService.relayMessages()` 改为：
   - 短事务领取批次
   - 事务外发送 MQ
   - 按 `worker_id` 完成状态迁移
5. 每分钟回收过期 `PROCESSING` 租约。

#### 测试

1. 两个线程并发领取同一批消息，单条消息只能被一个 worker 领取。
2. Worker 领取后崩溃，租约到期后重新进入 `PENDING`。
3. MQ 发送失败，消息进入退避重试。
4. 发送成功后重复完成请求不改变状态。

#### 验收

- 两实例 Relay 并发执行时，每条消息每轮只被一个实例发送。
- 进程在领取后崩溃，消息可以自动恢复。
- 消费者仍按 at-least-once 设计保持幂等。

### A2. 下单幂等最终约束

#### 当前问题

Redis 采用先读后写，两个并发请求可能同时未命中并创建两笔订单。

#### 表结构

新增独立幂等账本 `order_idempotency`：

```text
UNIQUE(user_id, idempotency_key)
request_hash
status: PROCESSING / SUCCESS / FAILED
response_json
lease_until
expires_at
```

独立账本避免修改四张订单分片表，也能保存首次响应并处理请求体冲突和执行中崩溃。

#### 代码修改

1. 短事务通过唯一键领取 `PROCESSING` 记录，并写 30 秒执行租约。
2. 创建订单、优惠券核销和账本 `SUCCESS + response_json` 在同一 MySQL 事务提交。
3. 相同 Key 和相同请求体回放首次响应。
4. 相同 Key 和不同请求体直接拒绝。
5. `FAILED` 或过期 `PROCESSING` 记录可以被后续重试重新领取。
6. Redis 旧幂等逻辑退出 HTTP 主入口，不再承担最终正确性。

#### 测试

1. 并发请求只允许一个请求领取执行权，其余请求回放首次响应。
2. 相同 Key 携带不同请求体时拒绝。
3. 执行失败或租约过期后可以安全重试。
4. Key 缺失时保持普通创建订单语义。

### A3. 多支付单重复成功治理

#### 当前问题

一笔订单允许多次创建支付单。两个支付单都收到成功回调时，第二个支付单可能更新为 `SUCCESS`，订单 CAS 更新失败后仍写支付成功 Outbox。

#### 状态设计

支付单状态：

```text
PENDING -> SUCCESS
        -> CLOSED
        -> DUPLICATE_PAID -> REFUND_PENDING -> REFUNDED
```

订单新增可选字段：

```text
active_payment_id
paid_payment_id
```

#### 代码修改

1. 创建新支付单时关闭该订单旧的 `PENDING` 支付单，设置新的 `active_payment_id`。
2. 回调事务中先锁定或条件更新订单：
   - `WAIT_PAY + active_payment_id == callback.payment_id` 才能进入 `PAID`。
3. 订单更新成功后再将支付单更新为 `SUCCESS` 并写 Outbox。
4. 已支付订单收到另一支付单的真实成功回调时，标记 `DUPLICATE_PAID`，写入异常事件，不发送正常支付成功事件。
5. 对重复扣款预留自动退款工作流，当前 Mock 场景可以落账并进入人工处理。

#### 测试

1. 两张支付单按顺序回调，仅一张进入正常 `SUCCESS`。
2. 第二张支付单真实成功时进入 `DUPLICATE_PAID`。
3. 重复回调同一支付单保持幂等。
4. 正常支付成功只产生一条支付成功业务事件。

### A4. 秒杀 Redis 与 MySQL 一致性闭环

#### 当前问题

Redis Lua 预扣成功后，MySQL Outbox 写入可能失败。Redis 与 MySQL 无法通过本地事务原子绑定。

#### 第一阶段实现

使用 Redis Stream 将库存预扣和事件写入放入同一 Lua 脚本：

```text
检查用户是否重复
检查库存
扣减库存
记录用户
XADD seckill:stream 事件
写结果状态 PENDING
```

Java 消费 Redis Stream：

1. 读取事件。
2. 在 MySQL 事务中写 `user_coupon` 或业务 Outbox。
3. 提交成功后 `XACK`。
4. 消费失败不确认，由 Pending List 重试。
5. 数据库唯一索引兜底重复消费。

#### 补偿表

新增 `seckill_reservation`：

```text
reservation_id
session_id
coupon_template_id
user_id
status: PENDING/CONFIRMED/COMPENSATED
created_at
updated_at
```

#### 对账任务

扫描长期 `PENDING`：

1. DB 已有券，标记 `CONFIRMED`。
2. DB 无券且事件仍可重放，重新处理。
3. 无法恢复时执行 Redis 补偿并标记 `COMPENSATED`。

#### 验收

- Lua 成功后 Java 进程立即退出，重启后事件仍可消费。
- 重复消费不会重复发券。
- 失败事件有状态、可查询、可重试、可补偿。

4. RRF 合并后进入 Reranker。
5. ES 不可用时允许退化为纯 Dense，并记录降级指标。

### C4. Query Rewrite 命名和实现

短期将 `_simple_rewrite` 改名为 `normalize_query`。

真实 Query Rewrite 必须独立实现并可关闭：

1. 仅对上下文依赖、口语省略或业务别名触发。
2. 保存原查询和改写查询用于评测。
3. 超时或模型失败时回退原查询。

## 7. 阶段 D：Agent Runtime 加固

### D1. 官方 interrupt/resume

迁移到 LangGraph 官方模式：

```python
interrupt(payload)
Command(resume=approval_result)
```

要求：

1. 审批记录与 `thread_id`、`run_id`、`approval_id` 唯一绑定。
2. 中断前的写操作幂等。
3. 重复 resume 返回已完成结果，不重复执行工具。
4. MySQL Checkpointer 持久化 pending writes。
5. 服务重启 smoke 覆盖挂起和恢复。

### D2. 上下文预算

1. 使用模型 Tokenizer 或 Provider usage 维护上下文预算。
2. 单个工具结果设置最大 Token 数。
3. 大 JSON 只保留白名单字段和摘要。
4. 对话压缩保持 tool call 与 tool result 配对。
5. 摘要保存事实、已执行动作、未解决问题和审批状态。

### D3. Tool Router 与执行安全

1. 只读工具允许并发。
2. 写工具、高风险工具和未登记工具串行执行。
3. 工具调用增加 timeout、retry policy、circuit breaker。
4. 相同工具和参数重复调用触发循环检测。
5. 工具 schema 变更进入兼容性测试。

### D4. 静态与动态数据边界

```text
静态规则、SOP、商家手册 -> RAG
订单、支付、库存、GMV -> MCP 实时工具
半静态门店资料 -> 带版本和更新时间的 RAG
```

Agent 回答动态数据时必须引用工具结果，不使用向量库中的历史快照替代实时事实。
